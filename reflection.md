# PawPal+ Project Reflection

## 1. System Design

### a. Initial design

Three core functions that must be implemented to provide value are:

1. Add a Pet
1. Add a Task
1. Define a recurrence for a Task (e.g., daily, weekly, every `n` days, etc.)

- Briefly describe your initial UML design.

The application should have 4 main Objects:

* Owner
    * Attributes
        * ID
        * Name
        * List of Pets
    * Methods
        * Add Pet
        * Remove Pet
        * Edit Pet
        * Get Pets
        * Get Tasks for Pets
* Pet
    * Attributes
        * ID
        * Name
        * Birthday (optional)
        * List of Owners
    * Methods
        * Add Task
        * Remove Task
        * Get Tasks
        * Edit Task
        * Edit list of Owners
* Task
    * Attributes
        * ID
        * Description
        * Date
        * Time (Optional)
        * Pet
        * Recurrence (e.g., daily, weekly, every `n` days, etc.)
        * Status (complete, incomplete, skipped)
    * Methods
        * Update status
* Scheduler
    * Attributes
        * Owner
    * Methods
        * Get Owner's Tasks
        * Sort Owner's Tasks
        * Filter Owner's Tasks
        * Get Tasks by day

- What classes did you include, and what responsibilities did you assign to each?

Owners can have 0..* Pets. Pets can have 0..* Tasks.

Owners can add/remove/edit Pets, get Pets already associated with themselves, and get Tasks for associated Pets.

Pets can add/remove/edit Tasks, get a list of their own associated Tasks, and edit their list of associated Owners.

Task can only update its status. An Owner's visibility into Tasks can only come through their associated Pets.

### b. Design changes

- Did your design change during implementation?
- If yes, describe at least one change and why you made it.

Yes. The AI assistant caught an oversight, in that the every `n` days never had anywhere to define `n`. This change also required more changes to Tasks, and now daily recurring Tasks are generated by the previous occurrence's status updating to complete.

## 2. Scheduling Logic and Tradeoffs

### a. Constraints and priorities

- What constraints does your scheduler consider (for example: time, priority, preferences)?

Scheduler sorts Tasks by date, time, then priority (in tiebreaker order). It also assumes that the Task list is fully populated when generating a schedule. The Current Tasks list is a much better representation of the data rather than the schedule that comes out of **Generate schedule**.

- How did you decide which constraints mattered most?

The nature of this repository means that there are comments already pre-populated that hint at application behavior. At earlier points in the project, it was hard to reconcile which hints were referencing features I was missing and which hints were referencing features that I was going to address in later Phases. The lack of Owner preference was due to my treating the CodeHub project documentation as true over the README.

### b. Tradeoffs

- Describe one tradeoff your scheduler makes.

My Scheduler also only checks for eaxct start time overlap.

- Why is that tradeoff reasonable for this scenario?

It _could_ be reasonable for this scenario, as something like an overlapping meal and medicine should probably not cause a conflict. It _could_ be unreasonable for this scenario, because an Owner can't walk a dog the same time another dog has to be at the vet.

I accepted the tradeoff regardless, as we were aiming for lightweight. If we get to it later, we can iterate.

## 3. AI Collaboration

### a. How you used AI

- How did you use AI tools during this project (for example: design brainstorming, debugging, refactoring)?

In Phase 1, I used a bulleted list to generate the UML, which was then used to generate the Skeleton. There was a bit of an unexpected hiccup in this Phase. I _thought_ I was being explicit in describing the attributes and methods, but the assistant didn't quite pick up on the differences.

In Phase 2, I went class by class, starting with the "smallest" unit of `Task`. After each class, I generated `pytest` cases. I moved to `Pet`, then `Owner`, then `Scheduler`, at each step creating more `pytest` cases. Vertical integration gave me confidence, as adding new classes did not break existing tests.

I also missed some requirements. I prompted the AI assistant with a small plan to introduce each new requirement (add to class attributes, update methods, update test cases, update demo script), and it asked for small clarifications. The plans were then executed as expected.

- What kinds of prompts or questions were most helpful?

I found that the (relatively) large job of adding a new requirement was performed quite well after giving it a list of things I think it should address. I gave it a 6-step plan that it agreed with, and I liked that I could notice that it spent more time actually processing and making changes, and I could see it progressing through the list.

### b. Judgment and verification

- Describe one moment where you did not accept an AI suggestion as-is.

Originally, the logic to edit a `Task` was directly in the `Pet.edit_task` method. Though it would technically make sense for a `Task` to be edited by its "parent" `Pet`, I thought the logic for actually changing the `Task` Object made more sense to live in `Task`.

- How did you evaluate or verify what the AI suggested?

It felt like the most important thing to evaluate myself was every time the actual application logic (in `pawpal_system.py`) was created. I skimmed the response from AI to make sure it didn't trip up on anything, then immediately  tried to make sure I understood what the code did before reading the response thoroughly. Then, I'd make sure that its explanations in the response matched what I thought was happening. I also _immediately_ asked for `pytest` cases after code was generated. The cases covered the generated code, and old test cases did not break.

## 4. Testing and Verification

### a. What you tested

- What behaviors did you test?
- Why were these tests important?

The test coverage is actually quite large, as I asked for unit tests after every class implementation change. It was important to keep checking the unit test status while adding new, real Objects instead of mock Objects. It helped reassure that adding Pet did not break Task, and adding Owner, did not break Pet or Task. Reciprocally, Task did not need to know the implemenation details of Pet, and Pet did not need to know the implementation details of Owner.

### b. Confidence

- How confident are you that your scheduler works correctly?
- What edge cases would you test next if you had more time?

I think I'm only 4/5 stars confident. The **Current Tasks** view seems like what we _actually_ want, and I think that section is 5/5 stars confident. I think that the **Build Schedule** section misses the mark. I also think I am missing an owner "preference" at the time of writing.

## 5. Reflection

### a. What went well

- What part of this project are you most satisfied with?

When the AI made changes and suggested the next changes to make, sometimes the scope of the original change causes the volume of suggested next steps to increase. I was satisfied by coming up with a plan myself and proposing it, then watching the AI moving from file to file to edit as per the plan.

### b. What you would improve

- If you had another iteration, what would you improve or redesign?

 I think I would ask for clarification on the requirements. I think this is just a product of having to maintain multiple sets of directions in CodePath courses and in code repos themselves. In my experience, the client's requirements must be clear in order for us to implement the desired features.

## c. Key takeaway

- What is one important thing you learned about designing systems or working with AI on this project?

Using different sessions with different focuses was helpful. The chat for business logic, the chat for Streamlit application logic, and the general application chats all had appropriate context to answer the prompts.
